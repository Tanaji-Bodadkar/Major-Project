# ML methodology and status

## Implemented prototype

The application maps a `TelemetrySnapshot` to the canonical nine features listed in `docs/dataset.md`, selects those columns in the same order for training and inference, then applies a persisted scikit-learn median `SimpleImputer` and `StandardScaler` followed by a persisted regressor. The preprocessor is fit only on the training partition. CPU, RAM, disk, network and GPU values use the units shown in that dataset specification.

The present target is `measured_power_w` for legacy compatibility. It is generated by a mathematical formula, not a meter. Therefore all metrics and plots currently produced by this training process measure performance against synthetic targets only. They do not support claims about real hardware accuracy. No independent hardware validation has been performed.

## Split and model selection

The current generated rows have no timestamps, machine IDs, run IDs or workload IDs. The training code uses a deterministic random 80/20 holdout (`random_state=42`) because the data is IID synthetic. Calling this a temporal split would be incorrect. The model comparison reports MAE, RMSE and R² for LinearRegression, RandomForestRegressor and GradientBoostingRegressor on that holdout; selection uses the lowest holdout RMSE. With measured temporal/run data, use time-aware and/or grouped held-out runs or hardware to prevent related observations crossing partitions.

The estimator set is required to exercise the pipeline, not an endorsement of any model. Feature importances and held-out plots are also conditional on the synthetic generator and must be labeled accordingly.

## Missing telemetry

Missing feature values remain missing in feature preparation; no synthetic zero is inserted. The median imputer is learned from training features for numeric missing values. Live inference may therefore return a reduced-evidence estimate when GPU telemetry is unavailable, and reports which features were imputed. This allows the dashboard to function across devices without GPU telemetry, but does not make the estimate accurate: with the current synthetic target, the model cannot establish actual total power when GPU activity is unknown. Predictions remain explicitly marked as synthetic and unvalidated.

Other required telemetry values must be finite for prediction. Do not infer prediction confidence from model scores.

## Artifact contents

- `models/power_model.pkl`: selected fitted estimator.
- `models/preprocessing.pkl`: fitted imputer and scaler.
- `models/metadata.json`: feature names/units, target unit, dataset provenance/type, split, per-model metrics, preprocessing, training date and limitations.

Joblib artifacts must only be loaded from trusted project sources. Metadata marks this model as synthetic and hardware validation false.

## Train and evaluate

From the repository root:

```powershell
python notebooks/generate_training_data.py
python -m app.ml.train
```

Training evaluates the three models and creates comparison plots under `reports/figures/`. These are synthetic-target diagnostics, not measured evaluation. See `docs/dataset.md` before substituting a dataset; the loader validates columns, target values and invalid feature rows but does not solve feature-definition compatibility.

## Future measured evaluation

The HWiNFO workflow in `docs/measured-validation.md` can evaluate a separate CPU Package Power target using aligned Windows telemetry. Its candidate is CPU-only and must not be used as whole-laptop power or for device-level carbon estimates. For an operational whole-laptop estimator, obtain appropriately scoped wall-input measurements, reconcile definitions/units, use run- or hardware-held-out evaluation, report coverage and missingness, and validate on the intended hardware. Neither kind of validation has been completed yet.
